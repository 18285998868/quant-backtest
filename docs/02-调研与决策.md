## 1. 调研方法与证据分级

检索日期:2026-11-16。所有版本号以当日 crates.io、PyPI、GitHub Releases 和 docs.rs 为准。

使用的一手来源:

- crates.io API:版本号与发布时间。
- docs.rs:API 文档与版本页。

## 3. 五条路线

### 路线 A:自研事件驱动核心(推荐)

核心思路:

- 以 bar 为事件单位,维护统一时间线;策略在收盘读取当前及历史 bar,输出目标权重;引擎在下一根 bar 开盘撮合。
- 账本、成交、成本、保证金、止损、指标、报告全部自己实现,契约由本项目定义。
- 数据层用 Arrow/Parquet 列式存储,策略层用 Rust trait,参数扫描用 rayon 任务级并行。

成熟度:自研系统属于早期采用;所用组件(Arrow、Polars、rayon、serde)为生产可用。

对约束的适配度:高。

- 纯 Rust,无 Python 运行时。
- 成交语义完全可控,能精确实现"收盘信号、次日开盘"和两种止损触发。
- 多市场、做空、共享账户可按需求裁剪。
- 报告与指标同源,JSON/HTML 可控。
- 不引入 LGPL。

代价:

- 正确性责任在自己:账本、保证金、止损边界、指标公式都要测试。
- 单人约 4 周,时间紧;确认加入 walk-forward 与逆波动率后调整为约 5 周。
- 需要自己处理数据契约与外部 `data-reader` 的适配。
- 没有实盘/仿真的一致性保证。

已知失败案例:

- 没有找到与本设计完全相同的公开失败案例;这一类系统的常见失败是未来函数、幸存者偏差、成本低估和过拟合,见第 6 节文献。
- 事件驱动框架的固定开销有实测参照:NautilusTrader issue #5342 报告,在 2.0.0rc7 上,25 万根 1 分钟 bar、10 个标的、无策略无订单时,开启 bar execution 为 770 ns/bar,关闭为 210 ns/bar,约 560 ns/bar 花在空撮合上。说明"每 bar 都走完整撮合栈"会显著变慢;自研热路径必须避免这种开销。https://github.com/nautechsystems/nautilus_trader/issues/5342

证据强度:中。组件和失败模式有高证据;整套自研方案能否在 5 周内达到性能与正确性目标,未验证。

### 路线 B:NautilusTrader 作为内核

核心思路:

- 直接使用 NautilusTrader 的 Rust 回测引擎、撮合、账户、多 venue 模型;策略用 Rust 或 Python;报告自己写。
- 复用其生产级事件驱动架构和多资产支持。

成熟度:生产可用。31.6k stars、4.3k forks、22.5k commits,2026-11-16 仍有提交;支持加密、美股、外汇、期货、期权等多 venue。https://github.com/nautechsystems/nautilus_trader

对约束的适配度:中。

- 优点:多资产、多 venue、订单类型、账户模型成熟;回测与实盘同一套策略代码。
- 缺点:LGPL-3.0,与"MIT/Apache 兼容"的默认约束冲突,需要法务确认。
- v2 正在 RC,README 明确 API 仍可能 breaking;v1 只收安全补丁。把有限工期的项目绑在迁移中的 API 上风险高。
- Python 是主要控制面;纯 Rust 策略可用,但文档和示例以 Python 为主。
- 参数扫描不是内置能力,需要自己包一层;每个任务启动一个 BacktestEngine,固定开销不低。
- 依赖体量大,编译与学习成本高。

代价:

- 集成 + 学习 + 报告,约 2–4 周,且受许可证约束。
- 需要把数据转换成 Nautilus 的 instrument/bar 模型。

已知失败案例/问题:

- issue #5342:空闲 bar 撮合约 560 ns/bar,作者统计在一年的 15 标的、150 万执行 bar 上约占 15% CPU。该 issue 已于 2026-10-16 关闭,测量基于 2.0.0rc7,后续版本可能改善。
- issue #5242:funding settlement 的去重集合对每个 instrument 的每个边界都保留,长时间运行查找变慢。https://github.com/nautechsystems/nautilus_trader/issues/5242
- v2 迁移期版本线分裂(0.68.0 crate / 1.231.0 PyPI / 2.0.0rc),是实际的集成风险。

证据强度:高。版本、许可证、issue、迁移状态都有官方来源。

### 路线 C:向量化列式回测

核心思路:

- 把信号、收益、仓位算成列;参数网格作为额外维度;用 Polars/Arrow 表达式和数组广播一次算完,不做逐 bar 事件循环。
- 代表实现是 vectorbt(Python);Rust 侧可用 Polars 自建。

成熟度:vectorbt 生产可用;Rust 自建属于早期采用。

对约束的适配度:中。

- 优点:简单策略的参数扫描极快;列式内存布局对缓存友好;报告数据现成。
- 缺点:路径依赖的止损、保证金、现金约束、共享账户很难向量化;强行做会把引擎变成半事件驱动。
- vectorbt 社区版缺少杠杆、期货合约乘数、限价单,这些在 PRO;许可证含 Commons Clause。
- 内存放大明显:issue #797 报告 700 万行 × 10 列、32 GB 内存机器,调用 `pf.value()` 时分配失败;issue #704 报告 `Portfolio.stats` 消耗大量内存。https://github.com/polakowo/vectorbt/issues/797 https://github.com/polakowo/vectorbt/issues/704
- 不是纯 Rust,违反约束。

代价:简单策略 1–2 周;一旦要止损/组合/保证金,需要重写为事件驱动,前期投入作废。

已知失败案例:上述内存问题;issue #42 请求保证金交易,说明社区版能力边界。https://github.com/polakowo/vectorbt/issues/42

证据强度:高(对 vectorbt 的边界);Rust 自建向量化引擎的速度为推测。

### 路线 D:barter-rs 库组合

核心思路:

- 用 barter 的 Engine、Strategy、RiskManager、TradingSummary 做事件循环和订单管理;自己补数据、组合账本和报告。

成熟度:早期采用。2.4k stars、391 forks、510 commits,最后推送 2026-08-24;MIT。
https://github.com/barter-rs/barter-rs

对约束的适配度:中低。

- 优点:MIT;原生 Rust;事件驱动;文档称可高效跑数千个并发回测;自带 PnL/Sharpe/Sortino/Drawdown 摘要。
- 缺点:README 的法律声明明确写"仅教育目的,不打算用于商业部署、实盘或生产",与"研究验证"目标不完全冲突,但说明维护者不承诺生产质量。
- 数据集成以加密交易所为主,没有美股/外汇数据适配;需要自己写。
- 组合账户、保证金、跨市场语义需要确认;框架的 Engine 状态管理较重,可能要"跟框架搏斗"。
- 91 个 open issues,维护者单人为主,长期风险。

代价:1–2 周上手,之后可能为了组合/报告改框架内部。

已知失败案例:官方免责声明本身是最明确的边界;未找到美股/外汇组合回测的公开案例。

证据强度:高(自述边界);适配成本为推测。

### 路线 E:Rust 数据层 + Python 回测引擎

核心思路:

- Rust 负责数据下载/清洗/规范化,Python 用 vectorbt、backtrader 或自写 pandas 回测,QuantStats 出报告。

成熟度:生产可用。

对约束的适配度:低。

- 违反"纯 Rust"约束。
- Python 与 Rust 之间的数据传递、环境复现、部署复杂度增加。
- 参数扫描受 Python 内存和 GIL 限制;vectorbt 的内存问题仍存在。
- 报告生态成熟(QuantStats、Plotly),但许可证与依赖更多。

代价:首日最快,两周后开始还技术债。

已知失败案例:vectorbt 内存 issue;Python 回测框架的成交假设通常更简化,需要逐项核对。

证据强度:高(约束冲突明确)。

## 5. 对推荐方案 A 的反面检验

主动寻找的反对意见和失败模式:

1. "不要自己写回测器"是行业常见建议。理由是回测器最容易在细节上骗自己:未来函数、幸存者偏差、成本低估、公司行动、借券、流动性。NautilusTrader README 也强调研究向量化与生产事件驱动的分离,以及回测与实盘仍存在 venue、时序、持久化差异。自研不能消除这些,只能通过测试和披露控制。
   - 证据:官方文档 + 回测方法论文献;证据强度高。
2. 未来函数。若策略在 t 收盘看到 t 的 close 并在 t 收盘成交,就是使用了不可能获得的信息。本设计强制 t+1 开盘,但仍有隐患:用当日 high/low 判断止损、用调整后价格、用完整历史计算指标。需要逐项测试。
3. 成本低估。M3 已建模 Binance 期货资金费;融券费、隔夜利息、市场冲击仍未建模,只做 bps 手续费/滑点/成交量上限。对外汇 carry、美股融券与非 Binance 合约,结果仍可能偏乐观。报告必须披露,并提供成本敏感性。
4. 过拟合。1000 组参数扫描几乎必然出现高 Sharpe。若报告只按 Sharpe 排序,会系统性误导。必须提供样本外、walk-forward、DSR、参数敏感性;walk-forward 已纳入首版 S5,但窗口选择本身仍可能过拟合。
5. 性能。逐 bar 动态 dispatch、每 bar 分配 Vec、每任务重复加载数据,都会让 1.25B bar 步的目标失败。Nautilus 的 560 ns/bar 空撮合是警示:框架开销可以吞掉大部分预算。必须热路径零分配、任务级并行、早期基准。
6. 组合会计。做空、保证金、现金、目标权重、再平衡交互复杂;一次符号错误就会产生"看起来合理"的曲线。必须以手算夹具逐笔对账。
7. 开发周期。5 周内同时做正确性、性能、组合、walk-forward、报告,范围偏大。阶段门禁和"不做清单"是必要约束。
8. 数据契约。`data-reader` 归档字段、时区、复权方式若变化,适配可能返工;M2 已用真实归档和等价 CSV 对照固定时间戳与哈希语义,见 7.8。
9. 维护成本。自研引擎的每个新策略、新市场、新成本项都要自己加;Nautilus/barter 至少分担了事件循环和订单管理。
10. 机会成本。5 周写引擎的时间没有用于研究策略;如果目标只是验证少量简单想法,向量化或现成引擎更划算。

对反对意见的回应:

- 目标不是"造一个通用回测平台",而是"一个语义透明、能快速扫参、报告可复核的研究工具"。自研的边界被刻意限制在日线、三市场、两种触发、两层组合。
- 用"最小事件驱动 + 列式数据 + 任务并行"而不是全功能框架;不做 tick、不做实盘、不做 DSL。
- 通过手算夹具、样本外、DSR、成本披露来控制自欺。
- 若 2 天 spike 或首阶段基准不达标,按第 7 节触发条件改选 B 或 C,不硬撑。

## 6. 事前复盘:假设半年后失败

| 排名 | 最可能原因 | 提前信号 | 预防/应对 |
| --- | --- | --- | --- |
| 1 | 成交语义错误,结果不可信 | 手算夹具反复对不上;实盘/仿真与回测偏差大;止损成交价总偏向有利方向 | 阶段 1/2 表驱动测试;同 bar 止损优先;跳空用开盘价;报告披露假设 |
| 2 | 性能不达标,扫描仍要几十分钟 | 阶段 1 基准 < 1M bar 步/秒(2 核);每任务分配明显;CPU 利用率低 | 热路径零分配;SoA;rayon map_init;先做缩放基准;必要时改 Nautilus 或向量化 |
| 3 | 范围膨胀,5 周只完成一半 | 第 1 周结束还没有端到端;报告章节不断增加;组合需求反复变 | 固定不做清单;每阶段可交付;报告固定 10 个章节;变更需记录 |
| 4 | 数据契约不匹配,适配反复返工 | 真实样本字段/时区/复权与假设不符;加载器需要不断加特例 | 先要真实样本;规范 schema 加校验;适配层隔离;必要时直接对接 `data-reader` |
| 5 | 过拟合导致策略上线/评审失败 | 参数热图呈孤立尖峰;样本外大幅衰减;DSR 不显著;换参数结果跳变 | 样本外 70/30;walk-forward;DSR;参数敏感性;报告不承诺收益 |

补充风险:多币种/多日历误用、保证金会计错误、依赖升级破坏。它们要么在启动时拒绝,要么有专门测试。

## 7. 决策记录

### 7.1 决策

采用路线 A:自研事件驱动核心,配套:

- 数据:CSV 用于测试与通用输入;生产归档通过 path 依赖直接调用 `data-reader` 的 `binance-core`/`dukascopy-core`。阶段三设想的 Parquet/Polars 读取未落地,由归档直连取代。
- 策略:内置双均线、通道突破、截面动量 + `Strategy` trait。
- 执行:收盘信号、下一根 bar 开盘成交;止损/止盈支持 Intrabar 与 Close 两种触发。
- 组合:引擎内多标的共享账户;系统级多策略按收益序列合成。
- 扫描:rayon 任务级并行,每任务独立账户,指标流式汇总,只保留 top-K 曲线。
- 指标/报告:指标模块统一计算;HTML 单文件 + JSON;ECharts 6.1.0 内嵌,Apache-2.0;Askama 模板。
- 许可:项目 MIT/Apache-2.0 双许可;不引入 LGPL 运行时依赖。

确认后补充:自动线程/内存预算、逆波动率权重、周期契约、walk-forward,见 7.7。

### 7.2 放弃的选项及原因

| 选项 | 放弃原因 |
| --- | --- |
| B NautilusTrader | LGPL-3.0 与许可约束冲突;v2 RC 的 breaking API;Python 控制面;参数扫描需自建;学习/集成成本不低于自研裁剪版 |
| C 向量化 | 止损、保证金、共享账户、再平衡是路径依赖,向量化会变成半事件驱动;vectorbt 非纯 Rust 且有 Commons Clause;内存放大 |
| D barter-rs | 官方免责声明"仅教育用途";数据集成以加密为主;美股/外汇与组合语义需大量自建;长期维护风险 |
| E Rust + Python | 违反纯 Rust 约束;环境与内存问题;不解决核心成交语义问题 |
| 自研 DSL/脚本 | 通用条件表达式会变成语言实现,维护成本高;内置策略 + Rust trait 已覆盖 |
| 直接上分布式/GPU | 目标负载在 8 核单机可完成;过早引入复杂度 |

### 7.3 关键假设

沿用 `./01-需求规格.md` 第 8 节 A1–A19。最关键的五条:

1. 数据可映射到规范 schema;周期由配置声明,M1 已支持分钟/小时/周线。
2. 一次回测统一计价货币;跨资产类别只在收益层合成。
3. 目标机 8 核以上;当前 2 核只做验证;线程数自动检测,结果与线程数无关。
4. 默认无杠杆、成本可配置;Binance 期货资金费已建模,融券费、隔夜利息与展期仍不在首版。
5. 5 周单人,范围按"不做清单"裁剪;walk-forward 与逆波动率已纳入,多周期核心已按 M1 实现,分块流式加载已按 M4 实现。

### 7.4 触发改选的条件

| 条件 | 动作 |
| --- | --- |
| S1 基准 < 1M bar 步/秒(当前 2 核),或外推 8 核 < 4M/秒 | 暂停,分析热点;若 3 天内无法解决,改选 B 或 C |
| `data-reader` 归档字段/路径变化,适配超过 3 天 | 固定上游版本或只 vendor 必要 crate;仍失败则退回 CSV 导出 |
| S3 结束仍无法通过组合/保证金手算测试 | 砍掉共享账户,退回"独立回测 + 收益层组合" |
| 报告实现超过 1 周 | 砍到核心章节,参数敏感性/DSR 延后 |
| 逆波动率/ walk-forward 超出 4 天 | 先保留 rolling walk-forward,逆波动率退回等权并在变更记录说明 |
| 用户要求分钟线/tick 或实盘 | 停止,重新做需求与选型;当前架构只预留周期契约,不覆盖高频 |
| 许可证审查拒绝 LGPL(若考虑 B) | 维持 A;不引入 LGPL |

### 7.5 值得先做的小规模验证(确认后执行,3 天)

1. 用 1 个标的 10 年日线 CSV,跑双均线,和手算 6 根 bar 案例对账。
2. 同一数据跑空策略与 SMA,测 bar 步/秒;用 500 标的 × 2500 bar 合成数据跑 100 组参数,外推 1000 组。
3. 用 Polars 读一个规范 Parquet,验证 schema、时区、排序、空值。
4. 用 ECharts 6.1.0 内嵌渲染一张净值/回撤图,断网打开。
5. 用两个标的构造共享账户再平衡案例,手算目标数量与现金。
6. 两个标的 σ=1%/2%,验证逆波动率权重为 2/3、1/3,σ=0 时回退等权。
7. 260 根合成日线,自定义 train=120/test=40/step=40/embargo=1/warmup=20,跑 2 个 walk-forward 窗口,验证 embargo、warmup、OOS 拼接。

验收:第 1、5、6 项数值完全一致;第 2 项外推满足 AC12;第 3、4 项离线可用;第 7 项窗口边界与 OOS 净值可复算。任一项失败,按 7.4 处理。

### 7.6 已知风险

- Binance 期货资金费已建模;融券费、隔夜利息、展期与其他交易所的合约成本仍未覆盖,相应场景的成本仍偏乐观。
- walk-forward 已纳入 S5,但窗口长度、embargo、warmup 的选择本身仍可能引入过拟合;报告需披露窗口参数。
- 逆波动率依赖历史波动率估计,窗口短会放大权重;σ 无效时回退等权并告警。
- 多币种、多日历不支持;跨资产类别组合只是收益层合成。
- 自研账本的边界情况(部分成交、保证金追缴、停牌)需要持续测试。
- 目标机性能未实测;当前 2 核数据只能外推;自动线程检测在 cgroup 嵌套场景可能偏差。
- `data-reader` 归档格式随上游演进,path 依赖可能引入 breaking change。
- 多周期核心已实现;M4 已用真实 1m 与 4 标的 1h 验证分块与整段结果一致,超大样本的峰值内存与吞吐仍待目标机实测。

### 7.7 确认后的修改(2026-11-16)

用户在阶段四摘要后提出四项修改,均已并入契约与阶段计划:

| 修改 | 决策 | 影响 |
| --- | --- | --- |
| 性能按目标机器自动调整 | `threads = "auto"`;读取 `available_parallelism`、cgroup v2 `cpu.max`、cgroup v1/v2 内存上限;`bench --scale` 给 1/2/4/8 线程推荐值;保留显式覆盖 | 新增 `system` 模块与 AC16;S1/S4/S6 增加用例 |
| 组合逆波动率权重 | `w = direction × (1/max(σ,floor)) / Σ_active raw × gross`;σ 无效回退等权;只在调仓 bar 输出 | 新增 AC17;S3 增加 T3.7–T3.9;不做协方差/风险平价 |
| 日线只是首版,后续扩周期 | `Timeframe` 契约 + `periods_per_year` 覆盖;M1 已支持 `1m/5m/15m/30m/1h/4h/1d/1w`;分钟级分块加载留后续 | 新增 AC18;数据契约要求声明周期;分钟线内存估算进风险 |
| 补充 walk-forward | rolling/anchored、train/test/step/embargo/warmup、训练集选参、OOS 收益拼接、参数稳定性 | 新增 AC19 与 3.8 契约;S5 增加 T5.9–T5.13;报告仍 10 章 |

预算影响:原 4 周调整为约 5 周(24–29 个工作日)。若不接受 5 周,按优先级裁剪:先砍 anchored 只保留 rolling,再砍参数敏感性热力图,最后才考虑把 walk-forward 降为单次 70/30;成交语义与账本测试不砍。

### 7.8 归档直连(2026-11-16)

M2 把数据入口从“只读 CSV”扩展为“CSV 或 `data-reader` 归档”。

| 议题 | 决策 | 理由 |
| --- | --- | --- |
| 依赖方式 | `backtest-data` 以 path 依赖同级仓库的 `binance-core`/`dukascopy-core` | 不复制解析代码;跟随上游演进;避免 git rev 与本地开发冲突 |
| 首版 provider | Binance `spot/futures/um/futures/cm` klines;Dukascopy `bid/ask` 的 `1m/1h/1d` | 现有归档覆盖;支持矩阵由上游校验 |
| 配置 | 顶层 `[source]`,与 `run.data` 二选一 | 不破坏既有 CSV 契约;错配在配置阶段失败 |
| 时间戳 | Binance `ts = close_time + 1`;Dukascopy `ts = open_time + timeframe` | 对齐“ts 是 bar 收盘时刻”契约 |
| 日期窗口 | 请求起点前移一个 `timeframe`,装载后再按 `[start, end)` 精确过滤 | 避免跨日/跨周 bar 被归档文件名的日期切掉 |
| 缺失文件 | 只进入诊断,不补齐;单标的区间内无 bar 仍报错 | 与多标的时间线契约一致,不制造虚假 bar |
| 哈希 | `config_hash` 不纳入数据源路径;`data_hash` 覆盖实际内容 | 同一内容 CSV/归档得到相同哈希 |

真实数据验收:M2 用 Binance 1h/1m、4 标的 1h 组合与 Dukascopy EURUSD H1 运行;
Binance BTCUSDT 1h 与等价 CSV 的 `data_hash`、`result_hash` 完全一致,
1/2 线程与重复运行一致。证据见 [M2 验收](../STEP.d/12-archive-source.md)。

### 7.9 资金费与合约成本(2026-11-16)

M3 在既有归档数据源上增加 Binance 期货资金费结算。

| 议题 | 决策 | 理由 |
| --- | --- | --- |
| 默认开关 | `futures/um`/`futures/cm` 默认启用;`spot` 与 Dukascopy 默认关闭;`source.funding` 可显式覆盖 | 永续合约的真实持仓成本;现货没有资金费,误开应在配置阶段报错 |
| 数据形态 | 每个标的存稀疏 `FundingSeries { ts, rate }` | 8h 一次,远少于 bar;按需推进光标,避免逐 bar 扫描 |
| 结算窗口 | 结算时刻落在 `(上一根 bar 收盘, 本根 bar 收盘]` 时,按费率求和,以本根收盘价计名义价值,在本根收盘扣现金 | 与“收盘估值”一致;1h 及更短周期精确,日线为近似 |
| 符号 | `cash -= qty × close × multiplier × rate`;正费率多头支付、空头收取 | 与 Binance 资金费定义一致 |
| 哈希 | 启用资金费时 `data_hash` 追加 `quant-backtest/funding/v2` 段;未启用时不追加;`config_hash` 不变 | 资金费是数据内容;开关由数据哈希覆盖,避免破坏旧配置哈希 |
| 结果/报告 | `BacktestResult.funding: Option<FundingSummary>`;JSON 新增可选 `funding`;HTML 单列净支出、付出/收到、结算次数与按标的明细;schema 升到 1.2 | 成本可见、可对账;未启用资金费时序列化省略,旧结果哈希不变 |
| 亚秒时间戳 | 归档 `calc_time` 向下取整到秒 | Binance 少量记录比整点晚 1–2ms;不归一会被分到下一根 bar,错用下一根收盘价 |

真实数据验收:Binance UM BTCUSDT 1h(2024-01)87 次结算,净支出
`-34.92654974212712`;独立复算与引擎差 `1.8e-13`;4 标的组合的
`funding.total_cost` 与 `by_symbol` 之和一致。证据见
[M3 验收](../STEP.d/13-funding.md)。M4 将资金费段标签升级为
`quant-backtest/funding/v2`,与数据哈希 v2 一起重录,结算语义未变。

### 7.10 分块流式加载与哈希 v2(2026-11-16)

M4 在不改成交、风控、资金费与指标语义的前提下,让分钟级大样本按窗口装载。

| 议题 | 决策 | 理由 |
| --- | --- | --- |
| 触发方式 | `chunk_bars > 0` 强制;否则仅当 `memory_limit_gb > 0` 且全量估算超限时自动 | 默认不多扫一遍数据;显式开关便于验收与排障 |
| 窗口语义 | 绝对下标 `[start, end)` 连续推进;块首带 `history_bars()` 根只读历史 | 策略指标与引擎下标不因切块漂移;历史不重复交易 |
| 状态延续 | `EngineState` 携带现金、持仓、挂单、目标权重、权益/成交/交易、资金费光标、告警与下一根下标 | 窗口只重建只读 `Universe`,不重置账户 |
| 窗口大小 | 单 worker 预算的一半,扣除时间线/资金费与策略历史 | 留一半给归档装载峰值与结果对象 |
| 哈希 v2 | 固定页 `PAGE_BARS = 65_536`,页摘要按标的名与总行数汇总 | 支持时间分块流式计算,与 `chunk_bars` 无关 |
| 资金费哈希 | `quant-backtest/funding/v2` | 与数据段同步升级,避免 v1/v2 混用 |
| 范围 | `run`/`validate`/`sweep`;`walkforward` 首版整段 | 先固定单次回测与扫描语义,walk-forward 后续复用 |
| 读取 | 归档按窗口读自然月;CSV 每窗口整文件扫描 | 首版不做稀疏索引,以时间换内存 |
| 兼容 | `config_hash` 不含 `chunk_bars`;历史 data/result/sweep 哈希重录 | 窗口不是配置语义;v2 是契约变更,旧哈希不再可比 |

真实数据验收:

- BTCUSDT UM 1m 2023-06,43199 bar,`chunk_bars=5000`:全量与分块
  `result_hash` 同为 `f648cd3e...`,`data_hash` 同为 `d9dc81d8...`;
  2338 笔交易、89 次资金费结算与告警逐项一致。
- BTC/ETH/BNB/SOL UM 1h 2024-01,744 bar,`chunk_bars=100`:全量与分块
  `result_hash` 同为 `54259a53...`,`data_hash` 同为 `da7521b2...`。
- `fixtures/s5_daily.csv` 的 4×4 网格,`chunk_bars=50`:全量与分块
  `sweep_hash` 一致;CLI 契约测试覆盖 run 与 sweep。
- 显式 `chunk_bars >= 数据长度` 回退整段;自动分块由单元测试覆盖。

限制:归档窗口仍克隆完整时间线与资金费;CSV 每窗口重扫;`sweep` 各 trial
独立读取,未共享窗口;43k bar 样本的进程峰值 RSS 由二进制基线主导,
内存收益需在超大样本与目标机上验证。证据见
[M4 验收](../STEP.d/14-chunking.md)。
